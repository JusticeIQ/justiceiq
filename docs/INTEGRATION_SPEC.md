# JusticeChamp ⇄ JusticeIQ Integration Specification

JusticeChamp (consumer intake) and JusticeIQ (lawyer portal) are designed as **two separate
applications with two separate databases**, connected through a narrow, consent-gated API surface
rather than a shared database. This keeps consumer data private by default and lets each product
evolve independently.

## Shared data objects

These are the objects that must round-trip between the two systems. Field names below match the
TypeScript types in each MVP (`justicechamp/src/lib/types.ts` and `justiceiq/src/lib/types.ts`) so
a future shared package could unify them.

| Shared concept | JusticeChamp source | JusticeIQ destination |
|---|---|---|
| Referral ID | Generated by JusticeIQ on receipt | `referrals.id` |
| Claim ID | `claims.id` | `referrals.source_claim_id` (external reference, not an FK) |
| Consumer consent record | `consent_records` (`share_with_lawyer` type) | `referrals.source_consent_id`, `consent_records.source_consent_id` |
| Claim summary | `Claim` (incident overview, key dates, parties, chronology, etc.) | `referrals.*` structured summary fields |
| Claim-readiness score | `ClaimScore` | `claim_assessments` |
| Document metadata | `ClaimDocument[]` (name, category, description — no binary transfer implied here) | `referral_documents` |
| Timeline data | `TimelineEvent[]` | `referral_timeline_events` |
| Consultation request | Triggered from JusticeChamp's "Request Lawyer Review" | `consultations` (status `proposed`) |
| Lawyer-match result | `LawyerMatch` | `referrals.assigned_lawyer_id`, `match_explanation` |
| Referral status | N/A (JusticeChamp shows a simplified status) | `referrals.status`, pushed back to JusticeChamp via webhook |
| Client communication status | Task completion / document requests | `communications`, surfaced back to JusticeChamp as read-only status |

## Data flow

1. **Consumer requests a consultation in JusticeChamp** → JusticeChamp calls JusticeIQ's `POST
   /api/referrals` (see `docs/API_SPEC.md`) with the claim summary, score, documents metadata,
   timeline, and a consent record reference. No document binaries are required in the initial
   payload — only metadata; actual files are fetched on demand via a signed, consent-scoped URL
   when a lawyer opens the referral, which is what `documents` metadata rows without content
   represent in this MVP.
2. **JusticeIQ creates a `referrals` row** with `status = 'new'`, runs firm/practice-area/jurisdiction
   matching, and assigns (or leaves unassigned for manual triage).
3. **Lawyer actions in JusticeIQ** (accept, decline, request more info, schedule consultation,
   convert to matter) update `referrals.status` and, for status changes and consultation
   confirmations, trigger a `PATCH` back to JusticeChamp (`docs/API_SPEC.md` →
   *Update referral status*, *Send client notification*) so the consumer sees status in their own
   dashboard without needing direct access to JusticeIQ.
4. **Document requests** raised in JusticeIQ (`Request More Information` / a document-request
   communication) call JusticeChamp's inbound webhook so the request appears in the consumer's
   Documents page, closing the loop without exposing JusticeIQ internals to the consumer.
5. **Conversion to a matter** is JusticeIQ-only; the source referral ID and consent record ID are
   retained on the resulting `matters.source_referral_id` for auditability, but no further
   automatic sync occurs unless the firm shares an update back to the consumer.

## Consent model

No claim data is shared with a specific firm until the consumer has taken an explicit
"request consultation" action in JusticeChamp and granted `share_with_lawyer` consent scoped to
that firm. JusticeIQ never queries JusticeChamp directly; JusticeChamp is always the initiator of
the referral-creation call. Consent revocation in JusticeChamp should trigger a `DELETE`/anonymize
call against the corresponding JusticeIQ referral if it has not yet been converted to a matter.

## Audit trail

Every cross-system exchange (referral created, status pushed back, document request sent, secure
message sent) is expected to be written to `activity_logs` on the JusticeIQ side and to
JusticeChamp's own `activity_log` table on its side, each tagged with the shared referral/claim ID
so the full exchange can be reconstructed from either system independently.

## Authentication between systems

Server-to-server calls are authenticated with a shared secret (`JUSTICECHAMP_WEBHOOK_SECRET` in
`.env.example`) sent as a signed header, not a user session token. Neither system's Supabase
service-role key is ever exposed to the other system or to the browser.
